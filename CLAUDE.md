# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**布丁喵 PUDDING MEOW** is an ordering system for a dessert shop in Melaka, Malaysia. It consists of two standalone HTML files + one SQL setup script — no build system, no package manager, no framework.

| File | Audience | Device | Purpose |
|------|----------|--------|---------|
| `pudding-meow.html` | Customers | Mobile (390px) | Browse menu, build cart, place & track orders |
| `pos.html` | Staff | Desktop (1366×768) | Point of sale, payment, pending-payment queue, admin dashboard, menu management |
| `supabase-setup.sql` | one-time | — | Creates DB tables, RLS, realtime, seeds the menu |

Both apps are pure vanilla JS with inline `<style>`/`<script>`. They share a **Supabase** cloud backend (`orders` + `menu_items` tables + Realtime + a few Edge Functions) so a customer's phone and the shop's POS sync across devices. Payment is mode-based: **堂食 dine-in** is counter-only (TNG link or cash/DuitNow at counter, staff confirm in POS); **外卖 delivery / 自取 pickup** use **HitPay** (hosted checkout, online e-wallet/DuitNow) so the order is prepaid before the kitchen starts. If Supabase is unconfigured/unreachable, both apps fall back to a localStorage-only mode (single-device). See `DEPLOY.md` to go live.

## Mini-program: `pudding-meow.html`

Mobile-first, capped at a 390px `.phone` container. Four screens are all in the DOM at once and toggled by `switchTab()` (adds/removes `.active`); a fixed `.bottom-nav` switches between them.

| Screen | `id` | Notes |
|--------|------|-------|
| 首页 Home | `screen-home` | Pixel-precise absolute-positioned canvas (`.hc-*` classes) — brand logo, welcome bar, dine-in/pickup/delivery mode cards |
| 点单 Menu | `screen-menu` | Category sidebar (`#catList`) + item list (`#itemList`, grouped into sub-category sections) + expanding search + product-detail sheet with flavor pills |
| 订单 Orders | `screen-orders` | Customer's own order history with status filters + order-detail sheet (status stepper) |
| 我的 Profile | `screen-profile` | Member registration, 联系店长 (WhatsApp), store hours & address |

### Menu data
`MENU_FALLBACK` (near the bottom of the script) is a hardcoded object of 6 categories — `special, classic, toast, boat, ice, drinks` — each `{cn, en, items:[{name, en, price, desc, flavors[]}]}`. It's only the offline fallback; the live `menu` is built from the cloud `menu_items` + `menu_categories` tables (see Categories below).

### Cart
`let cart = {}` keyed by `"cat|idx|specSel.join(',')"` → `{id, name, en, price, basePrice, image, specs, qty}`. In-memory only, lost on refresh. After any change call `renderItems()` + `updateCartBadge()`.

**Panel** (Figma 33:44) — `.cart-sheet` is a bottom sheet: 12px top corners, 16px gap, 100px thumb + 250px details per line, name rendered as 14px 中文 + 12px English inline, spec text below (`min-height:35px`, so lines without specs still align), a 79px −/qty/+ group, and a 1px rule after every line. The floating cart button doubles as the panel's bottom bar (`.cartbtn.s-open`) rather than being a child of the sheet.

**Drag handle** — the 100×4 line at the top (`.cart-grab`, Figma 845:1064) is draggable: fling down >80px closes the panel, pull up >40px adds `.tall` (max-height 80vh → 94vh), and a small downward drag while tall returns it to normal. The sheet follows the finger only downward — letting it follow upward would drag it off the top of the screen. Its hit area is widened by a transparent `::before` because a 4px line is unhittable with a thumb.

**修改 → detail sheet** — each cart line's 修改 calls `editCartLine(key)`, which parses the cart key back into `(cat, idx, specSel)` and reopens the product-detail sheet via `openSheet(cat, idx, {sel, qty})` with the original choices pre-selected and the button relabelled 保存修改. `confirmAddToCart()` then **replaces** that line (`delete cart[_editKey]`, qty = the sheet's qty, merging if the new spec collides with another line) instead of adding a second one, and reopens the cart. `closeSheet()` clears `_editKey`, so backing out leaves the line untouched. The checkout page's own 修改 is a separate path and is deliberately unchanged.

**Button** (Figma 586:763) — three sizes: empty `70×70` circle, has-items `145×56` pill, panel-open `361×56` bar; radius full, `padding:0 8px 0 52px`, 去结算 pill `39px` tall with `0 24px` padding. Panel-open sits `28px` off the screen bottom (Figma's panel `pb-28`, since the button is its last child). The mascot is `left:0`, **not** the `-13px` the Figma frame shows: that 63.45-wide box has 13px of empty space on its left and the artwork only starts at `+13`, so `-13` puts the *visible* mascot exactly on the pill's left edge. Our SVG has no such margin — copying `-13` literally pushed the artwork 13px past the pill, and since the pill is already only 16px off the screen edge, the whole button ended up hugging the edge. It is sized by **width** (`44px`, height auto) rather than by the frame's `70px` height: 44 + 8 = the `52px` padding the price sits behind, so the 8px gap is a fixed number instead of something that falls out of an aspect-ratio calculation. (The frame's 70px includes 9px of empty space at the top; taking it literally made the artwork 51px wide and left only 1px before the `RM xx.xx`.) The empty-state rule has to reset `width:auto` since that variant sizes by height instead. The badge is a child of `.cartbtn-ico`, so that box must be `width:auto` (sized to the image, not centred) or the badge drifts into the middle of the carton.

### 会员登录态
`refreshMemberProfile()` clears the session **only** when the server actually says the session is invalid — `_auth_member()` is the one place that raises 「登录状态无效，请重新登录」, and `_isAuthErr()` matches on that text rather than on the P0001 code (other RPCs raise P0001 for unrelated reasons like 「该手机号已注册」). It used to call `_memClearSession()` on *any* `res.error`, so a dropped request, a PostgREST schema-cache miss, or a rate limit silently logged the customer out. Nothing in the UI announces it beyond the member card reverting to the guest card, so the customer keeps ordering — as a guest. The order lands with `member_id` null, no XP/Coin is granted, and the shop only finds out by reconciling later.

### 会员手机号 / 生日（注册表单）
Member phones are stored in **one canonical shape: `0127010189`** — local format, digits only. They used to be stored exactly as typed (`+60 12-701 0189`, `6012 7010189`, `012-7010189` all coexisted), and `rpc_pos_find_member` compares digit strings, so a staff member reading `0127010189` off a ticket found nothing for a member stored with the `60` prefix. `_normPhoneMY()` (app) and `_norm_phone_my()` (DB, `supabase-member-birthday-phone.sql`) are the same rule: strip non-digits, `60…`→`0…`, bare `1…`→`01…`; valid = `^0\d{8,10}$` (01x mobiles 10–11 digits, 06 landlines 9). Register/login normalize before sending **and write the cleaned value back into the field**, so the customer sees what was actually stored. The server normalizes again — the client is not trusted — and both login and the POS lookup compare `_norm_phone_my(stored) = _norm_phone_my(input)`, so rows the one-time migration had to skip (two accounts collapsing onto the same number) still resolve. That migration deliberately **does not merge** those two accounts: XP/Coin/wallet/coupons hang off each `id`, so it skips them with a `raise notice` and leaves the call to the shop.

**`security definer` + `set search_path = public` 会让 `crypt()` 消失** (`supabase-fix-crypt-search-path.sql`). Supabase installs **pgcrypto into the `extensions` schema, not `public`**, so any function that pins `set search_path = public` and calls `crypt()` / `gen_salt()` / `gen_random_bytes()` throws `function crypt(text, text) does not exist` at runtime. This took down member login completely: `rpc_member_login` (from `supabase-member-birthday-phone.sql`) has the pin, so **every** login failed regardless of the PIN, while registration still worked because the `rpc_member_register` installed at the time was an older, unpinned version, and POS 重置 PIN kept reporting success because `rpc_admin_reset_member_pin` is also unpinned — it really was writing a correct hash that login could never read. The giveaway in the data is `members.last_active_at` sitting exactly at `created_at`: only `rpc_member_login` ever writes that column, so equal values mean the account has never once logged in. The repair **alters the search_path only, never re-creates the function bodies** — `rpc_member_register` has been rewritten by three different SQL files that twice lost each other's work, so redefining it here would risk dropping the `referrals` insert again. Anything new that uses pgcrypto must write `set search_path = public, extensions`.

**登录时按 PIN 认人，不是按号码挑一个** (`supabase-fix-member-login.sql`). `rpc_member_login` used to do `where _norm_phone_my(phone) = … limit 1` with no `ORDER BY`, so when one number had two accounts — exactly the case the migration above deliberately skips — Postgres returned an arbitrary row. POS's 重置 PIN writes to the `member_id` staff clicked, so staff would reset account A while login kept matching account B: the customer is told 手机号或 PIN 不正确 no matter how many times you reset it. The fix matches on `pin_hash = crypt(p_pin, pin_hash)` instead, so whichever account's PIN the customer types is the account they get into; behaviour is unchanged when the number isn't duplicated. It also adds `pin_hash is not null`, closing a hole where an account with no PIN let **any** PIN through — `crypt(p_pin, NULL)` is `NULL`, `NULL <> NULL` is `NULL`, so the guard's `raise` never fired and login simply succeeded. Diagnose a specific customer with `supabase-diagnose-member-login.sql` (read-only). Merging duplicate accounts is still left to the shop — XP/Coin/wallet/coupons hang off each `id`.

生日 is a **required** field on the registration form (`memRegBirthday` → `members.birthday`, which already existed but nothing ever wrote to it) — the level table has advertised 生日 perks all along, and an optional field everyone skips can't power them. It sits between 手机号 and PIN so that **邀请码 stays the last field**, pre-filled from `?ref=`. POS 会员运营 → 会员列表 shows it as a 月-日 column, red when it's this month.

It is the one field **not** stretched to `width:100%`. `input[type=date]` paints its own `dd/mm/yyyy` text plus a calendar icon, and that text is normal body colour rather than placeholder grey — so at full width it was the only box in a column of short grey hints that read as long and black, and looked like it didn't belong. It's sized to its content (170px) and given an `.empty` class (toggled on `oninput` and re-synced in `showRegisterForm`) that drops the text to the same grey as the other placeholders. Don't "fix" it back to full width — the boxes were already identical at 350×44; the mismatch was the content, not the geometry.

`rpc_member_register` has been rewritten by three different SQL files and two of them lost each other's work: `supabase-referral-v2.sql` writes the `referrals` row but keeps the old default level (lands on the 未注册 tier), `supabase-member-default-level.sql` fixes the level but drops the `referrals` insert. `supabase-member-birthday-phone.sql` carries both. Anything that touches this function again must too — losing the `referrals` insert breaks the whole invite payout chain silently.

### 会员等级 / 成长值条
Level numbering follows the POS 等级管理 table's **排序** column, not a count the app does itself: `_isGuestLevel()` treats `sort_order === 0` as the 未注册 tier (plus the legacy 游客/访客/guest name match), so the grey Lv.0 card reads its name from that row (`_guestLevel()`) instead of a hardcoded 猫咪蛋, and `_realLevels()` starts at 排序 1 → Lv.1. Without that, a shop whose first row is 排序 0 路过喵 saw the app call it Lv.1 and label the guest card with a name that exists nowhere in the admin. If no row has `sort_order 0` there is simply no Lv.0 tier and every level counts from Lv.1, with the guest card falling back to the hardcoded name.

**The 未注册 tier is enforced in the DB, not just in the app** (`supabase-member-level-guard.sql`). Seven different RPCs recompute `members.level_id` with the same copied snippet (`xp_required <= xp` → highest `sort_order`), and none of them knows `sort_order 0` is reserved — so a member with 0 XP lands on it whenever the first real level's threshold is above 0, and the POS (which prints the raw level name) shows a registered customer as 路过喵. Rather than patch all seven, a `before insert or update of level_id` trigger on `members` rewrites any assignment that lands on `sort_order 0` to `_member_level_for_xp()` — one choke point that also covers RPCs added later. The app's `_memDisplayLevel()` fallback stays as a display-side safety net but is a no-op once the data is correct.

The XP bar measures **0 → the next level's `xp_required`**, the same basis as the two labels beside it (`450/600 XP` and `再获得150 XP`). It used to measure the current→next *segment*, so the same 450/600 read 75% in text but drew 50%; worse, a member whose `xp` sits below their own level's threshold (server default level set too high) produced a negative ratio clamped to 0%, so the number climbed while the bar never moved. `.mem-xpbar i.has` gives the fill a 10px floor — 5/1000 XP is 0.5%, which is 1px on a 202px track and vanishes entirely under `border-radius:999px`.

### 每周任务 (Figma 227:126)
The 我的 page's left mini-card is 每周任务 (it replaced 邀请好友, whose code now lives in 邀请中心); 每日签到 sits beside it. Figma's widths are 136 + 16 + 209 = 361 but the phone's content box is only 358, so the fixed-content card holds 136px and 每日签到 absorbs the 3px — scaling both would miss both.

`weekly_tasks` rows are `checkin_streak` / `order_count` / `spend_amount` with a target; finishing **all** enabled ones pays one reward from `weekly_task_settings` (not one per task — the design only has a single overall %). `rpc_get_my_weekly` computes progress and grants in the same call, so there is no 领取 button; idempotency is the `member_weekly_rewards` primary key `(member_id, week_start)`, so a customer refreshing 我的 can't farm it. The week is Monday–Sunday of the **business day** (`week_start()` → `date_trunc('week', biz_date(now()))`), matching the Transaction dashboard — otherwise 「本周消费 2 次」 would disagree with the transaction list. `checkin_streak` is the longest consecutive run *within* the week (gaps-and-islands), not the all-time streak, so last week's run can't complete this week's task on day one.

### 优惠券的三层模型 (`supabase-coupon-rules.sql`)
`coupons`（券模板：面额/门槛/有效期）→ **`coupon_rules`（发放规则）** → `member_coupons`（券实例）。中间这层是后加的，加它的原因是原来「发给全体会员」写成 `insert … select id from members`，那是**对按下按钮那一刻的会员拍快照**，明天注册的新人不在快照里 —— 所以「新人注册就送券」用两层结构根本表达不出来。

A rule is `trigger_event` + `conditions`(jsonb) + `per_member_limit` + `total_limit` + 起止时间, and **one coupon can carry several rules**. Events: `register`, `order_paid`, `birthday_month`.

**Conditions are a generic facts-and-compare engine, not a list of hardcoded `if`s** — that was the first cut and it meant every new promo idea needed a backend change, which defeats the point of putting the rules in the admin at all. `_coupon_facts(member, ctx)` computes one jsonb of everything knowable at fire time (本单金额/用餐方式/支付方式/是否首单/历史单数/历史消费总额/等级排序/XP/Coin/钱包余额/注册天数/生日月/星期几/小时/月份) and a rule is just `{"all":[{"field":…,"op":…,"value":…}]}` evaluated by `_coupon_cmp`. Operators are `>= <= > < == != in not_in`. `_coupon_cmp` casts both sides to numeric when both parse as numbers, so `'9' >= '10'` is correctly false rather than a string comparison. The POS builds these rows from `_CPR_FIELDS`, whose entries carry an optional `ev` list so order-only fields never appear under 注册即送 — and switching the event **drops** condition rows that don't apply, because a condition that can't match would silently make the rule never fire.

**注册事件挂的是 `members` 的 AFTER INSERT 触发器，不是 `rpc_member_register`。** That function has been rewritten by three SQL files and twice lost the other's work, so a call added inside it would eventually be dropped again; a trigger also covers every registration path at once. Same reasoning as `supabase-member-level-guard.sql`.

**发券绝不能连累主流程** — both triggers wrap `_coupon_fire` in `begin … exception when others then raise warning`, so a broken rule loses a coupon but never blocks a registration or an order write. Verified by pointing `_coupon_fire` at a function that always raises and confirming registration still succeeds.

**重跑一份旧脚本会把新功能悄悄抹掉** — 好几份迁移都重建同一个函数（`rpc_list_mall_coupons` 被 mall-category / free-claim / image-pos 各建了一遍，`rpc_get_my_coupons` 被 my-coupon-image / image-pos 各建一遍，`rpc_redeem_coupon` 被 free-claim / limit-period 各建一遍），而每份脚本都写着「可以重复跑」。于是在 image-pos 之后再跑一次 free-claim，商城列表就换回没有 `image_pos` 的旧版 —— **「我的卷」照常跟着取景走（它读的是另一个函数），只有「兑好礼」不动**，症状偏得刚好让人往前端找。规矩：**一个列只要被任何一份脚本用到，每一份重建那个函数的脚本都要带着它**（free-claim / my-coupon-image 都 `add column if not exists image_pos` 并返回它）；实在带不了的（`rpc_redeem_coupon` 的计数周期要依赖 limit-period 才有的 `_coupon_period_start`），就让旧脚本**检测到新列时跳过重建**并 `raise notice`，而不是覆盖。

**「每人限领」可以按天/周/月**（`coupon_rules.per_member_period`，`supabase-coupon-limit-period.sql`）。原来它是**终身**的，所以「免邮券每周限领 2 张」只能每周复制一张新券模板 —— 券包里堆一排同名券，顾客分不清，统计也散了。加一列 `total`（默认，行为不变）/ `day` / `week` / `month`，数的时候只数当前周期内领的那几张，周期一过自动回满，店家不用点任何按钮。周期的口径**必须**跟营业日和每周任务一致（`_coupon_period_start()` 用 `biz_date()` / `week_start()`），否则「本周领了几张」会跟仪表盘、每周任务对不上，同一天读出两个数。计数比较的是 `biz_date(mc.issued_at) >= 周期起点`，不是原始时间戳 —— 凌晨 1 点领的那张属于前一个营业日。三条发券路径里只有 `_coupon_fire`（注册/下单/生日）和 `rpc_redeem_coupon`（商城兑换）吃这个周期；`coupon_codes` 的每人限领仍是终身的，兑换码本来就是一次性的东西。**`total_limit` 没有周期**：那是「这批券一共印多少张」的意思，本来就不该自己回满。

**不重复发** — `_coupon_fire` takes `select … for update` on the rule row before counting, so a retried registration or a concurrent order waits, re-reads, sees the row the first call just inserted, and skips. `member_coupons.source_rule_id` is what the per-member count is keyed on: counting by `coupon_id` would be wrong when one coupon carries two rules, since each rule's limit is its own. The order trigger additionally returns early when `old.status = new.status`, so the later `kitchen_printed_at` write on the same row can't re-fire it.

`birthday_month` has no scheduler (Supabase free tier has no cron) — `rpc_admin_run_birthday_coupons()` exists to be called manually or wired to a Routine later; it is safe to run repeatedly because `per_member_limit` still applies.

**发放条件 ≠ 使用限制** (`supabase-coupon-v2.sql`). The first cut expressed everything on the issuing side, so a coupon whose rule said 「只发给外卖顾客」 was still redeemable on a dine-in order — and 「20% OFF」 on a RM200 bill took RM40 off, because nothing capped it. Redemption limits now live on the **coupon template** and are enforced in `_coupon_calc` (the server is the authority; both front ends duplicate the same checks only to grey the coupon out early):

| 列 | 作用 |
|---|---|
| `max_discount` | 百分比券封顶（ZUS 券面上的 `capped at RM10`）。现金券不需要——面额本身就是上限 |
| `channels` | 可用的用餐方式 `dinein`/`pickup`/`delivery`；null/`[]` = 不限 |
| `valid_from` / `valid_until` | 绝对有效期，和 `valid_days`（发放后 N 天）**取先到的那个** |
| `applies_to` | `{"scope":"order"}` / `{"scope":"items","ids":[]}` / `{"scope":"cats","codes":[]}`，取代旧的单个 `menu_item_id` |

`channels` 的字面量跟 `currentMode` / `sales_channels.code` 一致（`pickup`），但发放条件里的 `mode` 事实历史上用 `takeaway` —— `_coupon_norm_mode()` 把两者归一，两边都能喂进去。`p_mode` 传空时**不拦**：旧版前端不会传，宁可放过也不要把付得起的顾客挡在门外。

单品/分类券仍然只打**一份**（沿用旧口径），命中多件时取**单价最高**的那一份 —— 服务端 `_coupon_item_price` 用 `max(price)`，两个前端也必须取最大，否则结算页显示的折扣跟实际扣的对不上。购物车行上没有分类，只有商品 id，所以前端要回 `_menuRawRows` / `_menuRows` 查 `cat`/`subcat`；照着购物车行读会让分类券在前端永远匹配不上，而服务端却匹配得上。

**三处重复配置已经合并掉**，别再往旧的那份写：`coupons.coin_price` → `coupon_rules`（`trigger_event='coin_redeem'` + `coin_price`，于是兑换终于也有了每人限领/总量/领取条件）；`coupons.issue_from/issue_until` → `coupon_rules.starts_at/ends_at`；`coupons.menu_item_id` → `applies_to`。旧列都还在表上（不删，免得没刷新的前端读到 undefined 就崩），但迁移之后一律置空，只有 `applies_to` 是单个商品时才回填 `menu_item_id` 给旧前端看。

**积分商城首页（Figma 816:1064）** — 标签条从红色头部里挪到下面的米色条上，只剩 **兑好礼 / 我的卷** 两个（设计稿的第三个「赚积分」店家暂时不做）。兑好礼按分区横排：`限定 / 现金回扣·折扣 / 免邮 / 合作 / 其他好礼`，每段一排 230px 宽的卡横向滑动（上图 98 高 + 下白条：券名 + 右侧 Paw Coin 价）。分区本身是一张 **`mall_categories`** 表（`code` / `name` / `sort_order` / `enabled`），店家在 POS → 优惠券 → 积分商城分区 里增删改，跟 `menu_categories`、`sales_channels` 一个模式：**`code` 建后锁定**（`coupons.mall_category` 存的就是它，改了等于把已归类的券全打散），名字随便改。删一个分区会先把挂在它下面的券 `mall_category` 置空（落到「其他好礼」），不会连券一起删。**「其他好礼」不是表里的一行**，是前端凭空补在最后的一段——做成一行的话店家一删它，没分区的券就从商城上消失了。表没建或离线时退回写死的四段（`_PM_SEC_FALLBACK` / `MALL_CAT_FALLBACK`，两个前端各一份）。每张券归哪一段仍是 **`coupons.mall_category`，由店家在 POS 上选**，不是从券的类型推的 —— 「限定」和「合作」本来就是营销概念，同一张券这个月放限定、下个月放合作，系统猜不出来；能推的只有免邮，但为了一件事只有一个地方管，四个分区一律走这一列。没选的落到「其他好礼」，**不会消失**。空分区整段不渲染，免得留一个光秃秃的标题。卡片上半部那块图来自 **`coupons.mall_image_url`**（店家在 POS 单独传），没有才退回券绑定商品的图，再没有是纯色块 + 爪印。

**图一律 cover 铺满，切哪一块由店家拖**（`coupons.image_pos`，`supabase-coupon-image-pos.sql`）。券没传券图时会退回绑定商品的图，而商品图是菜单那条路裁出来的 **380×310 方图**（`MI_CROP_W/H`），`cover` 进 2.35 的商城卡和 2.70 的券面必然切掉一大半 —— 而居中未必是布丁最好看的那一半。试过 `contain` + 黄底居中（不切，但留边），店家要的是满图，所以改成存一个取景位置：`image_pos` 就是 CSS 的 `object-position`（`'50% 35%'`），POS 上两个**真实尺寸**的预览框（345×128 / 230×98）可以直接拖，两个框共用一个值、同步刷新。null = 居中。

**没做成「给券再裁一张图」**：裁要过 `<canvas>`，canvas 一碰 SVG 就把它栅格化（券图上传那里已经栽过一次）；而且裁一次就把原图其余部分永久丢了，换个槽位比例还得重裁。存位置是无损的，SVG 也照样能拖。拖动的换算要按**溢出量**算（`d.overY = 渲染高 − 框高`，百分比变化 = `dy / overY × 100`），不是按框高 —— 后者在图只比框大一点点时会拖得飞快、大很多时又几乎拖不动。手指往下拖是露出更上面那部分，所以百分比是**减**。`_pmImgPos()` 只认 `数字% 数字%`，其余当没设过：这个值要进 inline style。

**券图的上传刻意不复用商品图那条路** — 商品图为了裁成统一比例会先画进 `<canvas>` 再导出 PNG，而 **canvas 一碰 SVG 就把它栅格化了**，矢量的意义全没。券图原样上传（`contentType` 照传），裁剪交给 CSS `object-fit:cover`，SVG 才能保持清晰。店家自己设计的图形/字体应该传 SVG；照片没法做成 SVG，那种要传 2 倍图（槽位 230×98 → 460×196）。保存时若图还在上传中会先等它，否则 `mall_image_url` 存进去还是 null，图白传。

卡片整张可点即兑换（230 宽塞不下一个按钮还留得住券名），Coin 不够的**压暗而不隐藏** —— 藏了顾客就不知道攒到多少能换什么。

**0 Coin = 免费领**（`supabase-coupon-free-claim.sql`）。原来兑换价必须 > 0，因为 `coalesce(coin_price,0) > 0` 这一个判断同时兼了两件事——「有没有上架到商城」和「要花多少 Coin」——挤在一起，「上架了但不要钱」就表达不出来（免运费券、新人礼、节日券全是这种）。拆开：**上架与否看 `coin_price` 是不是 null**，**价钱看它的数值**。前端三处都得跟着改口径，`(r && r.coin_price)` 这种写法会把 0 当成 falsy，免费券显示成「未上架」。列表按 `coin_price` 升序，免费的自然排最前，本来就该最显眼。**价格那一格照常是「爪印 + 数字」，0 也不例外** —— 不写「免费领」：这一格永远同一种写法，顾客扫过去比的是数字，0 本身就说明了它免费（试过写「免费领」，店家要的是爪印 + 0）。

**0 Coin 时「每人限领」是唯一的闸门** —— 免费又不限领，顾客连点就能无限领券。所以 `_coupon_rule_guard()`（`coupon_rules` 的 before insert/update 触发器）直接拒绝 `coin_price = 0 且 per_member_limit = 0` 的组合，POS 保存前也拦一次。拦在**配置端**而不是等顾客兑换时才报错：那是拿顾客的脸去接店家的配置失误。`rpc_redeem_coupon` 在 `coin_price = 0` 时整段跳过扣币——不锁会员行、不写 `delta = 0` 的流水，对账时那种 0 的行只会让人以为出过 bug。

**我的券（Figma 1124:1572）** — 券包和商城是同一套卡片语言（上图 + 下白条），只是**竖版铺满一行**：券面 345×128（两边各 24，卡间距 24），下面白条两行 —— 券名（14 粗）+ 右下角 `Left <b>N</b> days`。原来那张「100px 锯齿票根 + 右侧三行文字」的横版卡整张换掉了，`_pmStub()` / `.pm-my-stub*` 跟着删。券面优先放 **`coupons.mall_image_url`**（`object-fit:cover`，SVG 不糊），没有才是默认券面：左边大字面额（`RM` 24 + 数字 84，百分比券把单位挪到数字后面，免运费券写一行字）+ 右边探出来的 `logo.svg`，喵按稿子的比例定位（左 155/345、宽 234/345），下半截被券面裁掉。甜品券没有图时是**黄底 + 甜品图居中、不写大字** —— 券名在白条上已经写了一遍。

`rpc_get_my_coupons` 一直没返回 `mall_image_url`（`supabase-my-coupon-image.sql` 补上），所以前端还留了一条兜底：按 `coupon_id` 去 `_mallItems` 里回查图。不跑那份迁移也不会坏，只是**商城已下架、或压根不是从商城来的券**（注册赠券 / 兑换码 / 客诉补发）看不到券面图。

**两个槽位共用一张母图，不做两套素材** — 商城卡 230×98（2.35）和券面 345×128（2.70）比例差 13%。做两套的真实成本不是设计费，是**有人会忘记传第二张**，漏的那张比切掉 3% 难看得多；所以走行业默认的「一张母图 + 安全区」：母图 **680×270**（两个比例的中间值 2.52），重要内容留在中间 **630×250**，商城卡切掉左右各 3.4%、券面切掉上下各 3.3%，都只吃到出血。POS 的上传框旁边画了这张安全区示意图，仓库根目录的 `coupon-image-template.svg` 是可以直接套的设计模板（两条彩色参考线分别是两个槽位的可见范围，导出前删掉 `id="guides"` 那一组）。`coupons.voucher_image_url` 是**可选的覆盖**而不是必填的第二张：留空就用 `mall_image_url`，只有哪张券在券包里构图确实不好看时才补。图片服务按 URL 派生尺寸（Cloudinary / imgproxy / Supabase Image Transformation）解决的是分辨率和流量、不解决构图，而且**不处理 SVG** —— 主力素材是 SVG 时那条路几乎没有收益，所以没走。

POS 那两个上传框共用一套逻辑（`_cpnImg[k]` + `_CPN_IMG_EL[k]`，`k` 是 `mall`/`voucher`），写两份迟早改漏一边；`saveCpn()` 要等**两个**上传都完成才写库。库里还没有 `voucher_image_url` 这一列时（迁移没跑），保存会**去掉这一列重试一次**并说明原因 —— 券面图是选填的，不该因为它整张券都存不下来。

**券详情页（Figma 869:1584 兑好礼 / 1144:1382 我的卷）** — 两页共用一套骨架（`#cdScreen`）：返回条 + 128 高的券面 + 一列信息块 + 钉在底部的一颗按钮。差别只有三处：标题、要不要「Redeem Coins」那一格、按钮是 兑换 还是 使用。**做成两页迟早让两边的间距走样**，所以只有 `_cdRender()` 一处在决定长什么样；券面也只有 `_pmFace()` 一处，卡片和详情页共用。

「Validity」在两页是**两种口径**，不能混：商城里的券还没发出去，说的是「领到之后管几天」（`valid_days`）；券包里那张已经有到期日了，说的是「还剩几天」（`expires_at`）。顾客看到的必须是对他当下有用的那个数。「Method」由 `channels` 得来，空 = 三种都行，跟服务端 `_coupon_calc` 的口径一致。条款那三条是通用法律文本，**写死在前端**（`_CD_TERMS`）；券自己的说明是 `coupons.description`，店家在 POS 上填 —— 「买一送一怎么用」这种话只有店家写得出来。

**确认弹层不用 `confirm()`**（Figma 1145:1812 / 1145:1813）：系统弹框里放不下爪印，也跟不上这套配色。`_cdAskRedeem()` 是「确认使用 🐾100 兑换？」+ 兑换/暂不，`_cdAskShort()` 是「还需要 🐾50 才能兑换。」+ OK。所以 `redeemMallCoupon` 拆成了 `_doRedeemMall()`（只管发请求）+ 详情页那一步确认。

**结算页挑券也走详情页，不再有打勾**。原来是点卡＝选中、券面右上角压一个勾；现在两种模式点卡都是进详情页，选不选由那颗按钮决定：能用的写「使用」，**用不了的压暗并在按钮上方写明原因**（`#cdWhy`：`需满 RM100.00` / `只能用在外卖单` / `已使用`）。这样顾客进得去、看得到条款和门槛，才知道为什么用不了 —— 原来那种「卡片直接不可点」只会让人以为页面坏了。已选中的那张：卡片白条右边写「已选用」（顶掉天数），详情页的按钮变成「取消使用」。选和取消都算一次决定，做完都回结算页。`pmPickCoupon()` 仍然是挑券的唯一闸门（详情页的按钮状态只是显示，它才是真的判断）。

白条右边那格是**状态优先**：已使用 / 已过期直接写状态，比算天数有用；没到期日写「永久有效」。左边那格只写门槛（`满 RM20.00`），**无门槛就留空** —— 稿子这一行本来只有右边的天数，多写一句「无门槛」是废话。结算页挑券态（`_pmFromCheckout`）：已选中的写「已选用」，用不了的把原因写在白条右边**顶掉天数**，同时把左边的门槛清空 —— 「需满 RM20.00」已经把门槛说了。

**兑换码、免运费券、时段限制、使用报表** (`supabase-coupon-v3.sql`). 兑换码的两种形态是**同一张 `coupon_codes` 表的两个 `kind`**——`public`（一串大家都能用，靠 `max_uses` + `per_member_limit` 控量）和 `unique`（一人一码，`max_uses` 恒为 1）。分两张表就要把「时间窗 / 总量 / 每人限领」的校验写两遍，迟早改漏一边。码存**大写**且唯一索引建在 `upper(code)` 上，否则能建出两条只差大小写的码；一次性码由 `rpc_admin_gen_codes` **在服务端生成**（前端自造撞号只会静默少发几张），字符集去掉了 `0/O/1/I/L`——印在小票上顾客会看混。撞号自动重摇，连摇 20 次仍撞就报错让店家加长前缀。

**免运费券抵的是配送费，所以走 `_coupon_calc` 里单独一条路**，`return` 在适用范围判断之前。走通用那条会被结尾的 `least(disc, p_subtotal)` 削掉：一张 RM0 商品 + RM8 运费的单会算出 0。`p_delivery_fee` 因此要一路从结算页传到服务端。`max_discount` 在这里的含义是「最多免多少运费」，POS 的封顶输入框会跟着改标签。一单只能用一张券，所以免运费券会**占掉**那唯一的名额——真要和折扣券叠加，得先定叠加顺序和总折扣上限，那是另一个决定。

**时段限制按马来西亚时区判**（`_coupon_day_ok` / `_coupon_hour_ok`），跟营业日、每周任务一个口径。`usable_hours` 的 `from > to` 表示**跨夜**（21→2 = 晚 9 点到凌晨 2 点），`from == to` 当作不限而不是「只有那一秒」——否则店家手滑填成一样就把券锁死了。前端 `_cpnTimeWhy()` 复制同一套判断，注意 JS 的 `getDay()` 周日是 0 而服务端 `isodow` 是 7。

`rpc_admin_coupon_stats()` 的「带来营业额」用 `total - admin_fee`，跟仪表盘和月报同一个口径——三处不一致的话同一天会读出三个数。

**删券模板要分三种情况** — `member_coupons` 对 `coupons` 的外键**不是** `on delete cascade`（`coupon_rules` 和 `coupon_codes` 是）。这是对的：已使用的券是真实消费记录，不能因为店家删了模板就凭空消失。但原来的 `delCpn` 直接 `delete`，一旦发过券就被数据库拦下、弹一句英文外键报错，店员看着像「点了没反应」。现在先数一遍 `member_coupons`：有 `used` 的**拒绝删除**并指路「改用停用」；只有 `unused` 的，说清楚会连券一起收回再删；一张没发过的直接删。

`rpc_admin_issue_coupon` 现在**必须指定会员**：留空群发是对按下按钮那一刻的会员拍快照，明天注册的新人拿不到 —— 正是规则层要解决的问题。POS 的「发放」按钮只留客诉补偿用的单人补发。

### 邀请中心 (Figma 645:796 / 646:870)
Full-screen `#ivScreen` reached from the member grid, where it took 会员明细's slot per Figma 207:104. **会员明细 deliberately has no entry point right now** — `openMemberDetail()` and its page are still there, but the shop wants to decide later where it should live, so don't invent one. Rewards are settled **only when the invited friend completes their first order** — registering alone pays nothing, otherwise a pile of throwaway signups farms coins. One settlement pays three parties: the inviter, the friend themselves, and the inviter's inviter (二级, derived from `members.referred_by`, no extra table). `referrals.first_order_rewarded` is grabbed as the idempotency lock (`UPDATE … RETURNING … INTO` + `FOUND`), so a retried HitPay webhook can't double-pay.

All amounts live in `referral_settings` (single row, POS 会员运营 → 邀请规则). The customer-facing 邀请奖励 popup reads that same row, so what it advertises and what the server grants can never drift apart. `supabase-referral-v2.sql` also restores the first-order referral payout that `supabase-wallet-rules.sql` had silently dropped when it rewrote `rpc_on_order_completed`, and adds a ledger-based guard so the purchase XP/Coin can't be granted twice for one order.

The share icon copies/shares `?ref=CODE`; a page load with that query pre-fills the registration form's 邀请码 field. The QR box is still the grey placeholder the Figma itself shows — a real QR needs the shop's public URL.

### 往右滑＝返回（`_swipeBackInit()`）
左上角有返回箭头的页面**一律支持右滑返回** —— 顾客会先试这个手势再去找按钮。不写死一张页面清单：每颗返回键带一个 `pg-back` 类，启动时从它往上找到所在的整屏容器（第一个 `position:fixed` 的祖先；注册表单那种嵌在标签页里、没有 fixed 祖先的，就用返回键自己那一块，不要蔓延到整个 app），滑动时直接 `btn.click()` —— **「返回」是什么意思只有那颗按钮的 `onclick` 一处在定义**，以后新加页面只要给返回键加上 `pg-back` 就自动有手势。原来 `pmScreen` / `rcScreen` / `ldScreen` 各抄了一份一模一样的 IIFE，现在合并掉了。

`_swipeBlocked()` 挡掉三类起点，否则手势会互相打架：**横向滚动的容器**（商城那排卡、地址页那两个单行 textarea —— 在里面右滑是要滚它）、**地图和 canvas**（拖地图也是右滑）、**输入框**（往右拖是在挪光标或选字）。判定要求 `dx>80 && |dy|<60 && dx>|dy|×1.5`：斜着划多半是想滚列表，不该把页面关掉。

### Dining mode must be chosen before ordering
`currentMode` defaults to `'dinein'`, so a customer who taps 点单 straight from the bottom nav — never touching the home screen's mode cards — used to land in the menu with **no table number** and could order all the way through; the kitchen would get a ticket with nowhere to send it. `_modeChosen` tracks whether the mode was actually settled (home card tapped, or table/address confirmed in its modal) — `currentMode` alone can't tell "the customer picked this" from "this is the default". `switchTab('menu')` calls `promptModeIfNeeded()`, which opens the 堂食 table picker or the 外卖 address book (自取 needs nothing extra and just sets the flag). The modal is dismissible, so `openCheckout()` guards again: dine-in with no `_dineInfo` reopens the table picker instead of going to checkout.

### Checkout — `openCheckout()` / `confirmOrder()`
Cart → **确认订单** full-screen checkout page (`renderCheckout()`), which shows the delivery-address block only in delivery mode, and shows a **mode-gated payment method list** (`_ckSyncPayRows()`): 堂食 shows counter-only; 外卖/自取 show HitPay-only (`ckPayHitpay` row, `selectedPay='hitpay'`). `ckPayNow()` closes the checkout page and calls `confirmOrder()`, which builds an order object, `unshift`es it into `_orders`, persists to `localStorage['pm_orders']`, then calls `pmBroadcastOrders()` (see Integration). Payment branches on `selectedPay`:
- `tng` → opens the Touch'n Go payment link, order `status:'preparing'` (prepaid).
- `counter` → order `status:'pending'` (unpaid; staff collect at counter).
- `hitpay` → order is inserted as `status:'pending'` first, then calls the `hitpay-checkout` Edge Function for a hosted-checkout URL and redirects the page there via `_pmGotoPay()` (a thin wrapper around `location.href =` kept separate so tests can intercept it without a real navigation). See "Delivery + online payment" below for the full flow. In the UI (Figma 464:298) the single "online payment" splits into three rows — **Touch n Go** (`hp_tng`, TNG logo), **Online Banking** (`hp_fpx`, FPX lockup), **信用卡/借记卡** (`hp_card`) — all of which map to `payMethod:'hitpay'` (`selectedPay.indexOf('hp_')===0`); they currently all open HitPay's hosted page (no per-method hint passed yet). Logos are inlined base64 in `pudding-meow.html` (source PNGs `250px-*.png` also live in the repo root).
- `wallet` (Meow Wallet balance) → shown as an extra payment row (`ckPayWallet`) for **logged-in members only**, across all modes (`_ckSyncPayRows()` adds it alongside the mode default). `confirmOrder()` client-pre-checks balance, inserts the order `status:'preparing'` (prepaid), then calls the `rpc_pay_with_wallet` RPC (server-side: auths the member, checks balance, deducts, writes a negative `member_wallet_ledger` row, idempotent on `ref_id=order_id`). On failure (insufficient/race) the order is removed locally + voided in the DB. On success it settles XP/coin via `rpc_on_order_completed` and `refreshMemberProfile()`.

### 手续费 (admin fee — HitPay 通道费转嫁)
The customer pays HitPay's processing fee, itemised as 手续费 on the checkout page and added to `orders.total` (`supabase-admin-fee.sql`). Rates are copied verbatim from HitPay's published Malaysian rate card — Touch n Go `1.9%`, Online Banking/FPX `1.8% + RM0.40`, cards `1.2% + RM1` — and live in `shop_settings.admin_fee_rates` (jsonb, editable in POS Transaction → 手续费费率). `ADMIN_FEE_FALLBACK` in both HTML files is the offline fallback and **must stay identical in both**, exactly like the Supabase config block: if the two disagree, the customer sees one number in the app and the receipt prints another.

**The trigger is the payment method, not the mode.** `_adminFee()` charges only when `selectedPay` starts with `hp_` — a 自取 customer paying from their Meow Wallet has cost the shop nothing, and 堂食's counter cash never touches HitPay. Keying it off "mode is 自取/外卖" would bill both of them for a fee the shop never paid.

Payment-row icons come from repo SVGs (`FPX-Full.svg`, `credit card.svg`, `icon-recharge.svg`) rather than inlined base64. The logo slot is **40×24 with `object-position:left`**, not 24×24: FPX is a 114×56 lockup and a square slot squashes it to 24×12, visibly smaller than the square marks beside it. Rows whose icon is still an inline `<svg>` (柜台支付) need a `.ck-pay-ico` wrapper of the same width or their text starts at a different x — and that rule must be written `.ck-pay-row .ck-pay-ico` (two classes) to outrank `.ck-pay-row span{flex:1}`, which otherwise stretches the wrapper to 160px. The 价格明细 row says only 手续费 + the amount; the rate itself is a 10px `.ck-pay-fee` parenthetical after each payment method's name (`(1.9%)`, `(1.8% + RM0.40)`), written by `_ckSyncPayRows()` from the live rates rather than hardcoded in the HTML — so editing a rate in POS updates the labels too. Putting it there rather than on the 手续费 row means the three rates sit side by side where the customer is choosing, which is also the only place the comparison is useful. The rule resets `font-weight` because `.ck-pay-row.sel span` bolds the whole row, and 10px bolded turns to mush.

The base is the amount actually payable (`小计 + 配送费 − 折扣`), so the fee is computed **last**, after the coupon. `renderCheckout()` and `_doConfirmOrder()` both compute it and must agree — they are the display number and the charged number. `selectPay()` therefore calls the full `renderCheckout()` rather than just `_ckSyncPayRows()`: switching to 余额支付 has to drop the fee row, the total, *and* the amount on the pay button.

**The fee is not revenue** — it is collected and handed straight to HitPay. So `orders.admin_fee` is stored alongside the total (never recomputed: rates change, and recomputing would rewrite history), and it is subtracted in three places: the POS dashboard's 营业额 and the monthly report's 月营业额 (which must use the same basis or the same day reads 53.00 on one page and 53.63 on the other), and `hitpay-webhook`'s `rpc_on_order_completed` call, so members don't earn XP/Coin on a pass-through cost. The per-payment-method KPIs stay gross — that is the money that actually moved.

Two known limits, both deliberate and both documented in the POS dialog: **cards are billed at the domestic rate** (HitPay's international card is `3% + RM1`, but the customer hasn't swiped yet when they tap 信用卡, so charging 3% would overcharge every local cardholder), and there is **no gross-up** (HitPay bills on the grossed-up total, so copying 1.9% recovers ~1.864%; on a RM30 order that is RM0.01, not worth a checkout line reading 1.937%). The Online Banking row used to wear a **DuitNow** logo while routing to `fpx` — the customer saw one brand and paid another rail's rate. It now carries the FPX lockup (`FPX-Full.svg`) so the mark matches the rail. DuitNow itself (1.2% flat, no fixed fee — cheaper than FPX on every order size) is deliberately **not** offered as a separate method; the shop decided against it.

### Meow Wallet recharge (充值)
The 充值 page (`openRecharge` / `rcScreen`) picks a package then taps 充值, which calls `openRcPay()` — it no longer submits directly. That opens `#rcPayScreen`, a dedicated payment-method page reusing the coupon-detail skeleton (`.cd-screen`/`.cd-top`/`.cd-scroll`/`.cd-cta`) and the order-checkout page's payment-row/price-row visuals (`.ck-pay-row`/`.ck-pay-fee`/`.ck-price-row`). It offers four rows — **柜台支付**, **Touch n Go**, **Online Banking** (FPX), **信用卡/借记卡** — the same three HitPay methods the order checkout uses, minus Meow Wallet itself (topping up the wallet with the wallet makes no sense). `_rcSyncPayRows()` fills each HitPay row's fee-rate parenthetical from `_adminFeeDesc()`, the same helper the order checkout uses, so a rate change in POS updates both pages together.

**充值在线支付现在也收手续费** — it used to link straight to a generic HitPay checkout page with no `method` param and no fee, so with the shop's own HitPay fee-passthrough setting turned off, the shop was quietly absorbing HitPay's transaction fee on every online top-up. `rcPayNow()` (renamed from `doRecharge()`) now computes `afee = _adminFee(_rcPay, price)` exactly like `_doConfirmOrder()` does for a regular order, adds it to the order's `total`, stores it in `orders.admin_fee`, and passes `method` to `hitpay-checkout` so the hosted page opens directly on the chosen method. Counter payment is unaffected (`_adminFee('counter', …)` is always 0).

`rcPayNow()` inserts the order into `orders` with `ta_mode:'recharge'`, `status:'pending'`, `delivery_info:{recharge:{price, coins, package_id, …}}`. It appears in the **POS Pending Payment** queue tagged "钱包充值"; for counter payment staff click 已付款 and `markPaid()` detects `taMode==='recharge'` and calls `rpc_complete_recharge(order_id)`; for HitPay payment the `hitpay-webhook` Edge Function calls the same RPC once payment confirms. **The credited amount is `orders.total − orders.admin_fee`, not `total`** — `total` now includes the fee the customer paid to HitPay, and that money is never in the shop's hand to put in the wallet; crediting it 1:1 would hand the customer free balance equal to the fee. Server-side it credits `wallet_balance += credit` (+ `member_wallet_ledger`) and `coins += bonus` (+ `member_coin_ledger`), flips the order to `done`, idempotent (only while still `pending`). Recharge orders are filtered out of the customer's 订单 history and out of the POS sales dashboard/reports/member-spend (that money is counted when the wallet is later spent).

The authoritative `rpc_complete_recharge` now lives in **`supabase-recharge-admin-fee.sql`** (fee-aware crediting), which supersedes the version defined in `supabase-wallet-rules.sql` — that file's own definition is now wrapped in a guard (matching the `_coupon_free_claim`-style pattern) that checks a function-comment marker and skips redefining if the newer version is already installed, so re-running `supabase-wallet-rules.sql` after `supabase-recharge-admin-fee.sql` can't silently regress the fee back out of the wallet math. `rpc_pos_topup` (counter top-up from POS) is untouched — there's no `admin_fee` on that path.

### Delivery mode — address book + Lalamove quote
Picking 外卖 opens the address-book modal (`openDelivery()` / `dvModal`) — member addresses load via `rpc_list_my_addresses`; guests fill in the same form (`addrFormScreen`) but it isn't persisted. Selecting/saving an address fetches a delivery quote from the `lalamove-quote` Edge Function and stores it in `_deliveryInfo` (`address, lat, lng, fee, quotationId, recipientName, phone, addressId`). From the checkout page, the pencil icon (`ckEditAddr()`) reopens the address modal **as an overlay on top of the checkout page** (`_dvFromCheckout` flag) instead of navigating away; confirming refreshes the address + fee in place.

**新收货地址页 — 游客和会员是同一张表** — the guest version used to hide 地点名称/单位号/邮编/城市 and require only 地址+收件人+手机, so a guest's delivery order reached Lalamove without a unit number and the rider had to phone for it. Both now render every field with the same required set; the **only** difference is the bottom button (游客「确认」, used once and not saved; 会员「保存」 into the address book via `rpc_save_address`). `_addrCheckValid()` and `saveAddrForm()` share one list — if you re-split them, split both or the button will unlock on a form the save path then silently rejects.

The 地址 field is labelled **街道、小区**: 门牌号, 邮编 and 城市 each have their own box, so leaving the label as a generic 「地址」 invited customers to retype all of it there. `_fillAddrFromComponents()` (called from autocomplete, from 搜索, and from GPS 反查) writes only the street + neighbourhood segment into it — `_addrStreetLine()` joins `premise` / `route` / the 小区, and looks the 小区 up across `neighborhood` → `sublocality_level_1` → `sublocality` → `sublocality_level_2` because Google hangs Malaysian Taman names on any of the four, and not always the same one for a search hit vs a reverse-geocode of the same spot. Every write is guarded so a field Google can't resolve keeps whatever the customer typed.

**每一格只装它自己那一段**, so the split actually looks like a split: the place's `displayName` (店名/楼名) goes to **地点名称** via `_addrSetLabel()`, never into the street box. `_addrPlaceName()` first decides whether it *is* a name — a plain street address's `displayName` is「12 Jalan Merdeka」, which is a road, not a shop, so anything that is pure digits, equals the 门牌号, or contains the `route` is discarded. `_addrLabelAuto` tracks whether we filled 地点名称 ourselves: a customer's own「家」is never overwritten, but the name left by a previous search is, or changing your mind about the place leaves the old shop's signboard on the new address. There is deliberately **no "dump the whole formatted_address into 街道、小区" fallback** — that produced one long line containing 门牌+邮编+城市+店名, which is exactly what「没拆」looks like. When the components yield no street line, the box is left blank for `_addrFillMissing()` to fill from a reverse geocode instead. That helper runs **only when 门牌号/邮编/城市/街道 is still blank** and fills blanks only — a POI result usually carries neither `street_number` nor `postal_code`, and a required box nothing can fill leaves the button greyed forever. 城市 additionally falls back `locality` → `postal_town` → `administrative_area_level_2` → `administrative_area_level_1`.

**联想下拉必须防串包** — `fetchAutocompleteSuggestions` is only debounced, not serialized, so two requests can be in flight at once and the **slower, older** one can land last and overwrite the newer list. The customer sees the suggestion for the full address they typed, taps it, and gets the half-typed query's result — a street of the same name in another state. `_addrSuggSeq` drops any response that isn't the newest, and each rendered batch carries a `_addrSuggGen` stamped into every row's `onclick`, so a tap landing on a list that has since been replaced is ignored rather than resolving to whatever now sits at that index. Requests also carry `locationBias` (40km circle around `STORE_LATLNG`) + `origin`: `includedRegionCodes:['my']` alone is the whole country, and Jalan Merdeka exists in every state.

The dropdown's **first row is always 当前位置 Current location** (crosshair icon matching the map's locate button) — it renders even on an empty box or when Places returns nothing, so the customer is never facing a dead dropdown.

**下拉的行挂在 `pointerup` 上，不是 `click`** — on iOS, while the keyboard is up the first tap that lands on the page is often consumed by the system (dismissing the keyboard / scrolling the field back into view) and no `click` arrives until the second tap; the customer experiences「按一次没反应」. `pointerup` fires on the first tap. `click` is kept as well for desktop mice, and the two can't double-fire because `_addrCloseSugg()` bumps `_addrSuggGen`, so the trailing `click` arrives with a stale `gen` and is rejected. **That check must be read before `_addrCloseSugg()` runs** — a test caught the version that closed first and consequently rejected every single pick. `_addrTapStart`/`_addrTapEnd` drop the tap when the finger moved more than 12px, so scrolling doesn't select an address.

**选中一条之后必须掐掉还在飞的联想请求** — `_addrCloseSugg()` (hide + `_addrCancelSugg()` + blur) is the only correct way to close the dropdown, and `_addrPickSugg` calls it **before** the `gen` check so even a rejected stale tap leaves the UI clean. Just doing `classList.remove('show')` is not enough: a suggestion request already in flight resolves a moment later, calls `_addrRenderSugg()`, and that ends with `classList.add('show')` — the dropdown **reopens by itself** a few hundred ms after the customer picked something, which reads as「点了没关」.

The search box is a **single-line `<textarea rows="1" wrap="off">`**, not an `<input>`, read and written through `_addrSearchGet()` / `_addrSearchSet()`. A picked address is far wider than the box, and an `<input>` cannot be panned — its text only moves when the caret does, so the customer can read the first third and no more. A textarea is a real scroll container, so a finger swipe pulls the rest of the address into view. It is held to one line by `rows="1"` + a fixed 29px line-height/height, `white-space:pre`, hidden vertical overflow and hidden scrollbars; Enter is intercepted in `onkeydown` (it would otherwise insert a newline) and `_addrSuggest()` flattens any newline a paste brings in, since a second line would be invisible under the clipped height. **Two attempts to remove the「∧ ∨ ✓」bar the Android keyboard draws above it both failed and were reverted** — dropping the `<form>` wrapper, then making the box a `contenteditable` div. Neither made the bar go away, which is itself the finding: it is not the browser's form-field navigation, so no page-side markup change reaches it. The contenteditable also cost more than it saved (`blur()` on one does not reliably dismiss Android's IME, so picking a suggestion left the keyboard up). Don't try a third variation of this without first confirming from a screenshot which app draws the bar. The `<form>` is still gone and Enter is handled in `onkeydown`; that part is harmless and stays.

**「街道、小区」只拆出小区就等于没拆** — `_addrStreetLine()` returns `premise` / `route` / 小区 joined, but a POI result frequently carries **only** a `neighborhood` in `addressComponents`, with the road and the building/complex name living solely in `formattedAddress`. Taking that one-word result at face value put 「Kota Laksamana」 in the box while「Jalan KPKS 1, Kompleks Perniagaan Kota Syahbandar」vanished. So the line counts as usable only when a `route` or `premise` came back; otherwise it is discarded and `_addrTrimSegs()` re-derives it from `formattedAddress`, which still has every segment. Two things that path has to clean up, because `formattedAddress` is one flat string rather than typed components: the **house number leading the address**（「K5, Jalan KPKS 1, …」、「…, 1, Jalan KPKS 3, …」）is moved into 门牌号 when `street_number` was missing — matched by `_ADDR_HOUSE_RE`, which is kept deliberately tight (at most two letters plus digits) so 「Jalan KPKS 3」 can never be mistaken for a house number, and only ever applied to the first segment with something left behind it. And the **trailing state name**: we ask Google for `zh-CN`, so the last segment is typically 「马六甲」 while 城市 holds 「Melaka」 — the same place, unmatchable by string, so a last segment that is pure CJK is dropped by position.

`.addr-field textarea` — 街道、小区 is a single-line textarea for the same reason the search box is: the derived street line is regularly wider than the field, and an `<input>` can't be panned. The floating-label rules had to grow a `textarea` twin of each `input` selector.

**Delivery-fee buffer** — the fee shown to and charged to the customer is the raw Lalamove quote × `DELIVERY_FEE_MULTIPLIER` (default `1.2`, via `_dvCustomerFee()`). The 20% markup is a cushion: when staff later dispatch a rider from POS, Lalamove is re-quoted at the then-current (possibly higher) price, and the buffer means the shop rarely eats the difference. The buffer is applied **only on the customer side** — the POS dispatch flow shows the raw (un-buffered) Lalamove price as the shop's real cost.

**骑手实时追踪 (order-detail map)** — the order-detail sheet draws a Grab-style map: the real road route 店→顾客 plus a rider dot that actually moves. Two separate sources, deliberately handled differently. The **route** is one Google Directions call per order (`_trkDrawRoute` guards on `_trkRouteKey`) — it is billed per call and the path never changes, so recomputing it on every re-render would be pure waste; the store/dropoff markers are drawn *before* the Directions call returns, so a failed or unavailable Directions still leaves both endpoints on the map instead of a blank square. The **rider position** is `lalamove-driver` polled every 15s — Lalamove only refreshes it every 10s, so polling harder just re-reads the same point. A 403 from Lalamove is **not an error**: the endpoint is only live between "rider reached pickup" and "order complete", so it is mapped to `available:false` and the app simply doesn't draw the dot. A strip across the bottom of the map shows the rider's **straight-line** distance (`_trkKm`, haversine, computed locally). It is deliberately not road distance: that would need a Directions call on every 15s poll, and one order watched for ten minutes would bill dozens of them — so the label says 直线距离 rather than dressing it up as a navigation ETA. The distance is measured **to the shop before pickup and to the customer after** (`status==='PICKED_UP'`): measuring rider→customer while the food is still in the kitchen reads as "almost here" when nothing has left the shop. Orders in a terminal Lalamove state (`COMPLETED`/`CANCELED`/`REJECTED`/`EXPIRED`) still show the map but skip polling entirely — otherwise every historical delivery order a customer opens burns an Edge Function + Lalamove call that can only 403. `openOrderDetail()` is re-entered on every realtime update, so `_trkStart` no-ops when it is already tracking the same order; `closeOrderDetail()` clears the interval. Needs **Directions API** enabled on the same `GOOGLE_MAPS_KEY` the address picker already uses.

**Order → delivery persistence** — a delivery order's `confirmOrder()` also builds `order.deliveryInfo` (`address, lat, lng, recipientName, phone, remarks, fee, quotationId`) which `orderToRow` writes to the `orders.delivery_info` jsonb column (added by `supabase-orders-delivery.sql`). This is what lets the POS on another device read the dropoff coords + phone needed to dispatch a rider — the older per-field `deliveryAddress`/`deliveryCoords`/etc. are localStorage-only receipt fallbacks and do **not** cross devices.

## POS: `pos.html`

Fixed 1366×768 layout. PIN-gated (`localStorage['pm_pin']`, default `'0000'`). Two top-level views toggled by display:
- **`#posView`** — cart panel, T/A (dine-in/takeaway) toggle, menu grid, action bar, Cash + DuitNow numpad, **Pending Payment** modal (`showPending()`), change & print-ask overlays. `showPending()` labels `payMethod==='hitpay'` rows "在线支付" and hides the manual **已付款** button for them (they show "等待线上支付确认…" instead) — those orders should self-confirm via the `hitpay-webhook` Edge Function, so a staff member manually confirming one that the customer abandoned mid-payment would falsely mark it paid.
- **`#adminView`** — dashboard KPIs + transaction table (`renderDash`), members grid (`renderMembers`), monthly reports (`renderReports`).
  - **营业日 (business day)** — the shop sometimes trades past midnight and reconciles cash/DuitNow once at close, so a 01:30 order must land in the same day's totals as the rest of that night. `orders.business_date` is stamped **at insert time** by a trigger (`biz_date(created_at)` = local time minus `shop_settings.day_cutoff_hour`, default 04:00) — every insert path gets it without client code, and because it's stored rather than recomputed, changing the cutoff later never rewrites a day-end figure that was already reconciled. `rpc_next_order_num` resets on the business day too, otherwise a night that crosses midnight produces two #0001. POS reads the column via `_orderDay(o)` (falling back to a client-side `_bizDay()` for offline orders that haven't synced), and the cutoff is a select next to the Transaction date box.
  - **Transaction date box** — one pill (calendar icon + label) with a transparent `<input type="date">` laid over it; it shows 今天 Today (yellow) or `YYYY-MM-DD 周X` (white), capped at today by `max`. Days are keyed by a **local** `_ymd()`, never `toISOString().slice(0,10)` — that is UTC, and in Malaysia (UTC+8) it reads as yesterday until 08:00, so the shop would open on the wrong date. Picking a past day calls `loadOrdersForDay()`, which queries `orders` for that day's range and caches it in `_dayCache`: `_orders` only ever holds the latest 200 rows, so after midnight a busy yesterday gets pushed out of it and would otherwise show as empty. The fetch **merges** with any local same-day orders rather than replacing them, so an order that never synced still counts. `_findOrder()` looks in `_dayCache` as well as `_orders`, so Void/Print still work on a past day.
- **外卖配送 modal** (`showDelivery()` / `dlvBg`, blue header button with a待叫车 count `updDlv()`) — lists paid, active delivery orders (`deliveryInfo` present). Each shows recipient/phone/address/customer-paid fee + a **叫车 Lalamove** button. `dispatchLalamove(id)` first calls `lalamove-quote` for a fresh price and `confirm()`s "现在叫车运费 vs 顾客已付" (so staff never silently overpay), then calls `lalamove-order` to actually book the rider, writing the result (`orderId, status, shareLink, price`) back to `deliveryInfo.lalamove` (DB + broadcast). Already-dispatched orders show the live status (`_lmStatusText()` maps Lalamove codes like `PICKED_UP` → 已取餐·配送中), driver name/phone, and the `shareLink` tracking link; they can't be re-dispatched. The customer sees the same status + a 追踪骑手 button (opens `shareLink`) in their order-detail sheet (`odDeliverBlock`); status stays fresh because `lalamove-webhook` updates `delivery_info` and the realtime subscription re-renders.

**手动折扣 (`posOpenDiscount`, Figma 99:282)** — 控制栏的 Discount 打开一个套用 Price Panel 视觉的面板，两组切换：**整单 / 单项** × **百分比 / 现金**。

两组切换用 Figma 1096:299 那颗组件：两半拼死成一颗胶囊，选中那半橙底（`#D9641B`）白字，另一半橙描边黑字，只有外侧两角 12 圆角、中间接缝是直角。Figma 里选中态本身没有描边，代码仍给它同色描边 —— 少那 2px 会让选中的半边比另一半矮一圈，每次切换整排都跳一下。

面板上没有单独的「清除」按钮：数字盘左下角那颗 **✕ 是清空整个输入**（四个数字盘——收银/改价/折扣/桌号——统一都是这个行为，键面画的就是 ✕ 不是 ⌫，做退格是图标和行为对不上），清空后按 Done 就等于取消这笔折扣；Cancel 只是关面板。

单项折扣挂在 `cart[i].disc` 这个行对象上，**不是记一个下标** — 下标会随删行/加行错位，打给 A 的折扣会莫名跑到 B 头上；挂在行上，行没了折扣自然也没了。现金折扣按该行小计封顶，百分比拒收 >100。

整单折扣打在**扣掉单项折扣之后**的余额上（`_orderDiscOf(sub - itemDisc)`），否则两种折扣叠起来能超过应收。券仍然按**原始小计**判门槛和算折扣 — 改成按打折后的小计判会让本来能用的券突然用不了，那是另一个行为变更，不该混在这里。手动折扣和券可以同时存在，所以购物栏里是两行分开显示：合成一行就看不出钱少在哪。落单时 `orders.discount` = 券折扣 + 手动折扣。

**核对待付款单 (`_pendReviewOrder`)** — pressing **Payment** on a row of the pending queue loads that order into the cart for checking, where lines can be edited before the money is taken. While in this mode both **Delete** and **Delete All** touch **only the cart**: Delete All clears it and leaves review, and the order stays in the queue exactly as it was. Delete All used to void the whole order, which is far too destructive for what staff actually do here — they open a row mostly just to see what the customer ordered, since some customers pay later. Voiding has exactly one entrance: the 取消 button on each row of the pending modal.

**补绑会员** — customers forget to log in before ordering, and the order then lands with `member_id` null: no XP, no Coin, and the member's 消费次数/消费金额/每周任务 all silently miss it. So during review the `ctCustomer` phone box stays **editable when the order has no member** (`custEl.readOnly = !!o.memberId`) — staff type the phone, `posFindMember()` resolves it, and `_confirmPendPay()` binds `_posMember.id` onto the order, writes `member_id` in the same `orders` update, and lets `_settleMemberRewards()` credit the points. This is the fix-at-the-till version of `supabase-fix-order-member.sql`; doing it here means never having to reconcile it afterwards.

It **only ever fills a null** — an order that already has a member keeps the phone box `readOnly`, and `_confirmPendPay()` checks `!o.memberId` again as a second gate. Re-binding would move points from one customer to another, which is worse than the problem it solves.

**合并待付款单 (`mergePend()`)** — a table that orders in two rounds produces two pending orders; ticking 2+ rows in the queue merges them into one bill. Only **counter-paid meal orders** get a checkbox: HitPay rows must not merge because `hitpay-webhook` finds the order by id, so merging one away would leave a real payment with no matching row; recharge rows aren't meal orders at all. Non-mergeable rows render a `.pend-pick-sp` spacer so the order numbers still line up.

The surviving order is the one with the **lowest `orderNum`** — the kitchen and the customer already know that number. Items are concatenated rather than combined by name (differing specs make "the same item" ambiguous, and staff need to see what was actually ordered); `total`/`discount`/`admin_fee` are summed. The merged-away rows are **deleted, not voided**, matching `_cancelPend` — they never took money, so they aren't transactions, and voiding them would litter 交易明细. The cloud deletes carry a `status=pending` guard so a row another till just settled can't be removed.

Two refusals, both because there is no correct answer to pick automatically: orders bound to **different members** (whose points would the merged bill earn?), and a selection containing the order currently loaded in cart review (the cart would no longer match the order).

**Taking money must never be blocked by bookkeeping** — `_confirmPendPay()` and `askPrint()` show the change overlay / print before writing to Supabase, and wrap every write in its own `try`. They used to do the DB work first and touch the UI last, so a single throw anywhere in the tail (`db.from(...)`, `updPend()`, …) skipped the change overlay entirely — and with it the kitchen ticket and the receipt prompt, because both hang off `changeDone()`. The money was already in the drawer at that point and the kitchen never heard about the order. Losing a ledger row is recoverable; losing the ticket ruins the order in real time.

**制作单只能出一张，去重必须在数据库里** (`supabase-order-kitchen-printed.sql`) — `pm_printed_kitchen` is per-device *and per-tab* (it's read into memory at page load), so it can only stop a device from re-printing its own ticket. The real guard is an atomic claim: `update orders set kitchen_printed_at = now() where id = ? and kitchen_printed_at is null`, and only the device whose update returns a row prints. Both print paths must claim, and that is the part that kept regressing: `_scanPrepaidPrint` → `_claimAndPrintKitchen` claims properly, but the counter path (`_confirmPendPay` → `changeDone` → `printKitchen`) used to set only the local flag. So a 堂食 app order paid on till A printed there, then till B saw `pending → preparing` over realtime, found `kitchen_printed_at` still null, claimed it and printed a second ticket. `_confirmPendPay` now writes `kitchen_printed_at` **in the same `update` as `status`** — one statement, so by the time any other device sees the status change the column is already set and its claim必然 fails. If that write errors (the column doesn't exist because the migration was never run) it falls back to updating only the status columns: better to print twice than to leave a paid order stuck in `pending`. **Without the migration the whole scheme silently degrades to per-device dedup and every till prints one** — that is the first thing to check when duplicates come back.

**Supabase RPCs resolve with `{error}` rather than rejecting**, so a bare `.catch()` swallows every server-side failure. `_settleMemberRewards()` exists to keep the `rpc_on_order_completed` call in one place with a real `res.error` check plus a `showN()` — silently skipped XP/Coin looks identical to "the member wasn't bound" and can only be found by reconciling later. Anything money- or reward-shaped needs the same treatment (`rpc_pos_use_coupon` and `rpc_complete_recharge` already do).

Helpers: `sg/ss` (string get/set), `gj/sj` (JSON get/set) wrap `localStorage`. `showN(msg)` shows a transient toast.

## Backend: Supabase (cloud, cross-device)

Both files load `@supabase/supabase-js@2` from CDN and share **one config block** (`SUPABASE_URL` + `SUPABASE_KEY`, near the top of each `<script>` — **must be identical in both files**). `var db = window.supabase && configured ? createClient(...) : null`. When `db` is null (creds not filled, offline, or CDN blocked) both apps **degrade gracefully** to the local/offline path below.

`supabase-setup.sql` (run once in the Supabase SQL Editor) creates the schema, RLS, realtime, and seeds the menu:

| Table | Columns | Purpose |

Field mapping between the JS order object (camelCase) and DB rows (snake_case) is done by **`orderToRow()` / `rowToOrder()`** — defined identically in both files. `orderToRow` only emits real columns, so POS-only fields (`tender`, `change`, `customerName`) are dropped on insert.

**Menu** — the customer app (`loadMenu` → `buildMenuFromRows`) and the POS cashier grid (`loadMenu` → `buildPosMenuFromRows`) both read `menu_items`, so the POS admin **菜单管理** page (`renderMenuAdmin` + `menuAdd/menuEdit/menuToggleSold/menuDel`) is the single source of truth.

**Sold out (下架)** — `sold_out` items stay in the customer menu carrying a `soldOut` flag, rather than being filtered out. Removing them entirely left the customer unable to tell "we never sell this" from "today it's gone", so they keep hunting for it; the platform convention (greyed thumbnail + a SOLD OUT badge over the photo + no add button) says it in one glance. This is deliberately **not** how POS-only and channel-blocked items behave — those really must not be visible, so they are still dropped in `buildMenuFromRows`. Because the row is now visible, every add path needs its own guard: the row simply has no `onclick`, while `openSheet()` (reached from the quick **+**, search results, and 购物车「修改」) refuses with a toast, and `editCartLine()` checks before it closes the cart panel. The dim is a `::before` overlay, not `opacity` on `.item-thumb` — `opacity` would fade the badge sitting inside it. `applyMenu()` also runs `_dropSoldOutFromCart()`: an item marked sold out while the customer is mid-browse would otherwise sit in the cart and check out fine, since the cart line no longer disappears along with the menu row.

**Categories** — two levels, both cloud-editable (`supabase-menu-categories.sql`). A `menu_categories` row with `parent_code` null is a **top-level category** (the customer app's left sidebar, the POS cashier home's big cards); with `parent_code` set it's a **sub-category** of that one (饮料 → 奶茶 / 咖啡 / 果茶气泡). Items point at them by code: `menu_items.cat` = top level, `menu_items.subcat` = sub (null/'' = no sub, item just sits under the top category). `code` is locked after creation exactly like a sales channel's — item rows store the code. `enabled:false` hides a category from both apps but keeps it in the admin. Managed **inline inside POS 菜单管理 → 商品管理** (`itemsAdminHtml` + `mcAdd/mcEdit/mcDel`) — there is no separate 分类管理 tab: the page nests 分类 → 子分类 → 商品, with ＋新增分类 top-right, ＋子分类 in each category header, and ＋商品 in each sub-category header (`menuAdd(cat, subcat)` pre-selects the section you clicked from). Items whose `subcat` is empty — or points at a sub-category that was disabled or deleted — are listed in a 未分子分类 block at the top of their category, matching how the customer app renders them. The item form's 分类/子分类 selects are still how you move an item between categories. Deleting a top category is refused while it still has sub-categories or items; deleting a sub-category first clears `subcat` on its items (they fall back to the top category). Disabling a sub-category hides the tab, not the goods — its items still sell, untagged.

Both apps keep the old hardcoded lists (`CAT_ORDER`/`CAT_META`, `POS_CATS`/`POS_CATN`) purely as a **fallback** for when the table hasn't been created yet or the device is offline (also cached in `localStorage['pm_cat_cache']`); `catTops()`/`catSubs()`/`catName()` are the real accessors and are defined in both files. The POS cashier's category cards are no longer 7 absolute-positioned divs — `renderCatCards()` fills a 3-column auto-wrapping `#catGrid` whose metrics match the old Figma positions exactly, and `renderItemList()` adds a sub-category chip row inside a category (the chips filter the display only — `addItem` still gets the item's original index). The **customer app** groups them as sections instead of chips (Figma 21:4): `renderItems()` puts the un-sub-catted items first with no header, then one `.sub-title` bar (sky-blue, red tick, 「中文 ENGLISH」) per sub-category that has items. `buildMenuFromRows` supplies `menu[cat].subcats` (only subs that actually have items in the current mode) and `item.subcat`. **Rows are still keyed by the item's index in the whole category** — the sections are display-only, so `_itemRowEl(cat, idx)` gets the original index and cart keys stay valid.

**Search** (Figma 843:918) — the header's magnifier is a two-state component: collapsed it is just the 24px icon; tapping it grows a white pill leftward (`.menu-search.open`, 150×32, the icon's right edge stays put) with the placeholder 请输入商品. `onSearchInput` sets `_searchQ` and `renderItems()` branches to `_renderSearchResults()`, which matches name/en/desc across **the whole menu**, not just the active category — customers remember 抹茶 without remembering which category it hangs under. Hits are grouped under the same `.sub-title` bars, and each row is still built by `_itemRowEl(cat, idx)` with the item's original index, so adding to cart from a search result behaves exactly like adding from its own category. Clicking a sidebar category exits search (otherwise the sidebar looks broken — the results span every category).

**Sorting** — the five admin lists with a `sort_order` (`menu_items`, `menu_categories`, `spec_defs`, `sales_channels`, `recharge_packages`) are reordered by **long-pressing a row and dragging it**, not by typing 10/20/30. One shared helper drives all of them: mark the container `data-sortable="<table>"` and each row `data-sid="<id>" data-so="<sort_order>"`. On drop it renumbers 10/20/30… and writes back only the rows that actually moved, then reloads that table. It uses Pointer Events (HTML5 `draggable` does not work on touch, and the POS is usually a tablet) with a 400ms hold before a drag starts — otherwise a finger swiping to scroll the list gets mistaken for a drag.

商品管理 nests three sortable levels (categories ⊃ sub-categories ⊃ items), so a row only belongs to its **nearest** `[data-sortable]` ancestor — `_dsOwn()` enforces that in both the drop-target test and `_dsSave()`. Without it, dragging a category would sweep up every nested item row and renumber it against `menu_categories`. The flip side is deliberate: you can only reorder within one section; moving an item to another category/sub-category is done through 改, not by dragging across a boundary.

**Sales channels** — `menu_items.channels` and `spec_defs.channels` are jsonb arrays of channel `code`s; **null/empty means "open everywhere"**, so untouched rows keep selling in every mode. The customer app filters on them in `buildMenuFromRows()` (items) and `_itemSpecs()` (spec groups) against `currentMode` — the three built-in codes `dinein`/`pickup`/`delivery` are deliberately identical to `currentMode`'s values, which is why the POS refuses to let you edit a built-in channel's `code`. Switching mode calls `refilterMenuForMode()`, which rebuilds the menu from the cached raw rows, drops any cart line the new mode doesn't sell (item- or spec-group-blocked), and re-keys the cart by item id (`_remapCartKeys()`) because cart keys embed the item's **index** in the filtered menu. Channels are managed in POS 菜单管理 → **销售方式** (`channelsAdminHtml` + `chAdd/chEdit/chDel`); custom channels beyond the built-in three are backend labels only — the mini-program has no ordering entry for them. **The POS cashier grid deliberately ignores channels** — staff can ring up anything at the counter.

**Spec surcharges** — an option can add money, and the same option can cost different amounts on different items. Two layers: `spec_defs.option_prices` (`{"L":2}`) is the default, `menu_items.specs[i].prices` (`{"L":3}`) overrides it per item; absent means inherit (`_optAdd()`, defined identically in both files). A cart line's `price` is **base + the sum of the chosen options' surcharges**, and the line also keeps `basePrice`; each entry in `specs` carries its own `add`. **Coupons deliberately compute off `basePrice`** — the server's `_coupon_calc` reads `menu_items.price`, so `_posItemPrice()`/`_cartItemPrice()` must match it or the client would preview a bigger discount than the server grants. Receipts show the surcharge inline in the spec text (`L +RM2.00`) so the line price reconciles against the menu price. The hardcoded `MENU_FALLBACK` / `MENU_FALLBACK`-style objects remain as offline fallback and seed reference.

**Orders realtime** — both apps `subscribeOrders()` via `db.channel(...).on('postgres_changes', {table:'orders'})`. App `confirmOrder()` and POS order-save `insert`; POS `markPaid()` `update`s status. A customer counter order INSERTs → POS `loadOrdersFromCloud(true)` refreshes the 待付款 queue and toasts `🔔 新线上订单`. POS `markPaid` on an app order sets it to `preparing` → the customer's order flips to 制作中 live. The `hitpay-webhook` Edge Function does the same DB `update` as `markPaid` (pending → preparing) when a HitPay payment completes, so the customer's order flips live the same way without staff involvement.

### Edge Functions (`supabase/functions/`)
Server-side code that holds secrets the front-end must never see (browser source is public). Deployed to Supabase, called from the apps via `db.functions.invoke(name, {body})`. Both return HTTP 200 with `{ok:false, error}` on failure rather than a non-2xx status — `functions.invoke` swallows the response body on non-2xx, which used to hide the real error from the front end.

| Function | Called from | Purpose | Secrets (Edge Functions → Secrets) |
|----------|-------------|---------|-------------------------------------|
| `lalamove-quote` | app (delivery mode) + POS (`dispatchLalamove` re-quote) | Signs + calls Lalamove `/v3/quotations` for a delivery-fee quote to a given address; normalizes/clamps lat-lng decimals (Lalamove's regex rejects full browser-geolocation precision) and auto-swaps obviously-flipped lat/lng | `LALAMOVE_KEY`, `LALAMOVE_SECRET`; optional `LALAMOVE_MARKET`, `LALAMOVE_HOST`, `STORE_LAT`, `STORE_LNG`, `STORE_ADDRESS` |

## Order `status` vocabulary (shared)

`pending` (unpaid) → `paid`/`preparing` (paid, being made) → `ready` → `done`. The POS pending-payment queue filters strictly on `status === 'pending'`. The app's `STATUS` map treats `paid` as an alias of `preparing` (制作中).

**Delivery orders derive their progress from the rider, not from `orders.status`** — there is no "handed to the rider" action in the POS, so that column sits at `preparing` for the whole delivery and the customer would watch 制作中 long after the food left the shop. `_effStatus()` maps the Lalamove status instead (`LM_STEP`): dispatched (`ASSIGNING_DRIVER`/`ON_GOING`) → `ready` 骑手待取, `PICKED_UP` → `delivering` 配送中, `COMPLETED` → `done`. `delivering` is an **app-only display status** — it never exists in the DB, so the POS queue and the reports are unaffected. A failed dispatch (`CANCELED`/`REJECTED`/`EXPIRED`) deliberately maps to nothing and falls back to `orders.status`, leaving the order in 制作中 so staff can re-dispatch. An unpaid (`pending`) order never jumps to 待取 even if a Lalamove status somehow exists. The detail stepper is 5 steps for delivery (下单/制作中/骑手待取/配送中/完成) and stays 4 for pickup/dine-in; `_statusBadge()` relabels `ready` to 骑手待取 on delivery orders, since 待取餐 reads as "the customer collects it". `source` is `'app'` or `'pos'`; app orders set `tableName` to `📱线上·{堂食|自取|外卖}`. Prepaid **TNG** orders are `preparing` (not `pending`), so they're intentionally excluded from the pending queue. **HitPay** orders, unlike TNG, *do* start as `pending` (the order is inserted before the customer has actually paid on HitPay's hosted page) and only flip to `preparing` once the `hitpay-webhook` Edge Function confirms payment — so they briefly appear in the POS pending queue, but tagged "在线支付" with no manual confirm button (see POS section). Known MVP limitation: the app's 订单 tab shows all recent orders (no per-customer identity yet).

## Offline / local fallback layer (localStorage)

When `db` is null, or as a same-device backup, the apps still use `localStorage['pm_orders']` + a live-notify layer that predates the cloud:
- **`pmBroadcastOrders()`** posts on `BroadcastChannel('pm_orders_sync')`; each app also listens to the `window 'storage'` event. This only bridges **tabs of the same browser/origin** — it does NOT cross devices (that's what Supabase is for).
- Other localStorage keys: `pm_members` (POS members), `pm_pin` (staff PIN), `pm_ctr`/`pm_rm` (counter/reports), `pm_menu_cache` (last-fetched menu, for offline).

## Rendering Pattern

Both apps use full `innerHTML` re-renders of DOM subtrees — no virtual DOM, no reactive state. State lives in module-level `var`/`let` globals; re-render functions read those globals and rebuild the relevant subtree.

## Development

No build step. Edit the HTML file and refresh the browser.

**Cloud config:** put the same `SUPABASE_URL` + `SUPABASE_KEY` in both `pudding-meow.html` and `pos.html`, and run `supabase-setup.sql` once in the Supabase SQL Editor. See `DEPLOY.md` for the full launch guide (hosting + table QR).

**Local testing:** with real cloud, cross-device sync works over the internet — open the two files on two different devices. Without cloud (or to test the offline path), serve both from one origin so the localStorage/`BroadcastChannel` fallback bridges two tabs:

```bash
python3 -m http.server 8000
# http://127.0.0.1:8000/pudding-meow.html  (phone view: DevTools device toolbar)
# http://127.0.0.1:8000/pos.html           (another tab)
```

**Automated checks** (this repo's dev container blocks Supabase, so cloud round-trips can't run here): `node --check` the extracted `<script>` blocks for syntax; the Playwright scripts in scratchpad cover (a) graceful degradation when `db` is null and (b) cloud code paths via a mock `window.supabase` (verifying table names + `orderToRow` snake_case mapping + realtime wiring). Real end-to-end cloud verification happens in a normal browser.
